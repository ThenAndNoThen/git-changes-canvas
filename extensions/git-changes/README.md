# Git Changes

For installation, requirements, and sharing guidance, see the [repository README](../../README.md#installation-and-sharing).

A user-scoped Git diff canvas that never modifies the inspected workspace or downloads Git objects. All interface labels, hints, and errors are in English. The compact header contains branch comparison controls without the title/logo row, repository picker, Git command, or automatic-selection status row; aggregate change counts share the existing scope note. "Local" means that the Git object database already contains the required data, not that files must exist in the working tree; added, deleted, and un-checked-out files are supported. When opened in a repository session, the canvas resolves the current worktree from SDK `ctx.session.workingDirectory` (not the main checkout or the SDK's session artifact directory), selects the checked-out branch as target B, and loads changes automatically. Base A defaults to the remote default branch referenced by `origin/HEAD`, then the sole remote HEAD, the current branch's upstream, or finally HEAD. It never guesses main/master. Detached HEAD uses `HEAD`. Without a Git workspace or an explicit repository supplied through the canvas API, the canvas displays a no-repository message instead of opening a recently used repository. Branch inputs also accept tags, commit SHAs, `HEAD~3`, and other Git revisions; click "Compare / Refresh" or press Enter in an input to compare. Remote branches use existing local remote-tracking refs and are never fetched automatically.

Repositories without an initial commit still get their path and current branch filled in automatically. With uncommitted changes enabled, the working tree is compared with an empty tree, so staged and untracked files are reviewable before the first commit. Commit-only mode shows "No commits on this branch".

- **Since divergence · A...B**: follows the direction of `git diff A...B`, comparing the common ancestor with B to show B's changes since divergence using local Git objects. Swapping A and B changes the result. Missing or multiple merge bases produce an explicit error; use endpoint comparison instead.
- **Endpoints · A B**: compares two commits using `git diff A B` (or `git diff A..B`) without checking out their files.
- **Include uncommitted changes** (enabled by default): when B resolves to current HEAD, replace B's committed tree with a frozen snapshot of the owning worktree, including staged, unstaged and non-ignored untracked files. The final disk contents take precedence over staged text; explicitly staged ignored files remain included. A...B still uses the common ancestor of the two commits as its base. Other target revisions stay commit-only, as the scope note explains. Uncheck the option to compare only commits. Click "Compare / Refresh" to capture subsequent edits; file details never silently reread live disk contents.
- Search changed files on the left. Addition and deletion counts appear only when greater than zero (`+0` / `-0` are omitted; binary indicators remain). The right pane supports split/unified diffs, line numbers, word-level emphasis, wrapping, and horizontal scrolling. Added and deleted content has distinct green/red backgrounds and gutter accents in both light and dark themes. Drag the divider to resize the file list.
- Changed files follow the repository's directory structure in a collapsible tree. Directory counters show reviewed/total changed files, including descendants. Click a file's checkbox, or focus its tree row and press Space, to mark it reviewed without changing the open file. Each directory also has a checkbox that marks or unmarks all changed files under it, including subdirectories and filtered-out files, in one version-checked atomic update. A partially reviewed directory shows an indeterminate checkbox; clicking it or pressing Space on its tree row marks all descendants reviewed. While an update is saving, overlapping file and directory checkboxes are disabled. Once every changed file under a directory is reviewed, that directory and any completed ancestors collapse automatically. You can reopen them and uncheck files; root-level files remain visible. These marks track local review progress and do not submit or approve a GitHub or Azure DevOps review.
- File review marks are stored alongside repository preferences, keyed by worktree path and a fingerprint of the file path, status, and both compared object IDs and modes. They survive refreshes and reopening for matching versions; changed base or target content, including refreshed uncommitted changes, is unchecked unless that exact version pair was already reviewed. Unrelated file changes do not clear a mark. Review marks for different versions are independent.
- Filtering temporarily reveals matching directory paths without discarding the normal collapse state. Directory completion and bulk review always include all changed files under that directory, not just search matches. Arrow keys navigate and expand/collapse the tree, Enter opens a file or toggles a directory, Space toggles a file or directory's review checkbox, and Home/End move to the first/last visible row. Change and comment navigation reveal the destination file even inside a collapsed directory.
- In split diff and split full-file views, drag the divider between code panels, or focus it and press Left/Right, to adjust their widths. Headers, code columns, and independent horizontal scrollbars stay aligned. Each side keeps at least 160 pixels when space permits; narrower content areas use equal widths. The ratio is shared across files and views only within the current page, is not saved in repository preferences, and resets to 50:50 on page reload or reopening.
- Added files always show only the target version; deleted files show only the base version. Both diff and full-file views use a full-width single panel with no empty opposite panel or split-layout switch. Returning to a modified file restores the previous layout selection. An existing file emptied by a modification is still a two-version comparison. Empty added/deleted files retain their single-panel state, while binary files and unavailable text retain their explicit notices.
- Diff and full-file views support syntax highlighting for C#, Java, Kotlin, JavaScript/TypeScript, Python, C/C++, Go, Rust, JSON, XML, YAML, Markdown, and other common formats. Highlighting uses the complete local versions on both sides, so omitted diff context does not reset multiline comments or strings. Unknown formats use plain text.
- "Full file" supports "Split" and "Single column" layouts. Split view shows the complete comparison base (the common ancestor for `A...B`) and target B, aligning both sides by change blocks. Blank cells compensate for insertions and deletions without omitting unchanged content. Single-column view shows target B, or the base for a deleted file. Both layouts retain line numbers, syntax highlighting, wrapping, arrow controls, `F7` / `Shift+F7`, and cross-file navigation. Full-file and layout settings persist while navigating between files. In single-column view, pure deletions have navigable markers, including at the beginning or end of a file and when a file is emptied; these markers are not file content. Switching between full-file and diff views or layouts preserves the active change. Settings are saved per repository. Binary files and submodules explicitly report that ordinary full-text views are unavailable.
- Toolbar arrows, `F7` / `Shift+F7`, and `Alt+Down` / `Alt+Up` navigate change blocks, moving to the next or previous file in the filtered list at file boundaries. Binary and permission-only changes are also shown. Cross-file rename detection is disabled to avoid reading nonlocal rename candidates; renames appear as additions and deletions within the comparison. `Ctrl+P` focuses the file filter.

## Review comments

In diff or full-file view, hover over a line number and click the `+` on its left to comment on that line. Selecting code on one side also reveals a `+` beside the last selected line. You can click a line number, Shift-click another to select multiple lines, then click `+` to comment on the range. The control supports keyboard focus and Enter/Space; there is no separate toolbar comment button. References support partial-line columns and multiline ranges, with limits of 200 lines and 16000 characters. The server extracts the reference from the pinned Git blob (including a captured uncommitted version) rather than accepting arbitrary code text from the browser.

Clicking "Send to conversation" queues the comment into the session that owns this canvas through SDK `session.send`, not another open chat or a remote pull request. The main agent receives the file, revision, range, original text, and handling instructions. It uses `git_changes_review_read` / `git_changes_review_reply` to respond in the same thread when finished or blocked. Existing session mode, permissions, and approval flows are preserved; permissions are not elevated and workspaces are not switched automatically. Sending a comment uses the current session's model allowance. Missing persistent session storage produces an explicit error rather than falling back to temporary comments that would be lost.

New comments use SDK `displayPrompt` to appear concisely in the conversation as `Review inline code: path:L10`; follow-up replies appear as `Reply to thread: path:L10`. Multiline ranges use `L10-L15`. The agent still receives the full comment, pinned code reference, and handling instructions, and the original comment remains unchanged in the canvas. This is a compact message presentation, not the native review card's collapse protocol, and it does not rewrite previously sent messages.

Users can follow up with "Send reply" or choose "Resolve"; agent replies never resolve a thread automatically. Resolved threads collapse and move below all unresolved threads, retaining file/range order within each group. They can be expanded to view their history or reopened, which returns them to the unresolved group. The previous/next comment controls navigate unresolved threads by file and reference position, independently of diff navigation. They work across files and open the split full-file view when locating code. If the code changes, the original reference is preserved and marked outdated after refresh; old line numbers are never applied to the new version.

Prominent colored text badges distinguish waiting (amber), processing (blue), replied and awaiting the user's decision (green), uncertain delivery (red), and resolved (muted). Waiting includes sending and queued states; processing starts only when the agent calls `git_changes_review_read` for the latest unanswered comment, not merely when delivery succeeds. That processing marker persists across reloads. Each follow-up starts waiting independently of earlier replies. Status text and card accents make the state recognizable without relying on color alone.

Comments are stored in `files\git-changes-reviews.json` under the owning session's persistent storage directory (SDK `session.workspacePath`), organized by repository, comparison refs, and thread UUID. This is separate from the inspected Git worktree (`ctx.session.workingDirectory`). They do not depend on the panel's instanceId and are not written into the inspected code repository. They survive refreshes, panel reopening, and extension reloads. Panels in the same session receive synchronized replies. Failed or uncertain delivery preserves the comment and displays a warning; automatic retries are avoided to prevent duplicate handling. Check the owning conversation before resending. Unsent input drafts are not persisted comments and may be lost on page reload.

Use `open_canvas` with `canvasId: "git-changes"` and an instanceId of your choice. No path or branch is required. Optional input such as `{ "repo": "C:\\work\\repo", "base": "origin/main", "target": "HEAD", "mode": "merge-base", "includeUncommitted": true }` explicitly overrides automatic defaults; saved history does not override these parameters. The `compare`, `get_state`, and `get_file` agent actions are supported. `compare` accepts the same comparison options and returns at most 30 file entries, while the canvas displays the complete list. Its `includesUncommitted` field reports whether the target is a working-tree snapshot. `get_state` also returns workspace provenance and HTTP diagnostic counts. `get_file` accepts `includeSources: true` to return the complete pinned text for the comparison base and target; by default, it returns only the diff.

Comparisons use pinned commit SHAs and snapshot tree/blob IDs so branch movement or ongoing edits cannot make the file list and details inconsistent. Refreshing resolves refs again and checks whether historical objects are local. Working-tree snapshots copy the index into an OS temporary directory and write snapshot objects only there, using the original local object database as a read-only alternate. Sparse-checkout files retain their indexed contents. Git's built-in line-ending normalization is retained; external clean/process filters, filesystem monitors, external diff/textconv execution and repository scripts are disabled. A file normally transformed by a custom clean filter is therefore shown as its raw working-tree content, apart from built-in Git normalization. Submodules remain gitlink comparisons, not recursive working-tree diffs. Temporary snapshots are removed when replaced, when their panel closes, or on a failed comparison. The inspected index, refs, object database and working files are not modified. Each Git command has a 24 MiB output limit and a 60-second timeout; exceeding either produces an explicit error instead of truncation. File lists and details load on demand; narrow the range for very large comparisons.

Full-file views read the same pinned Git blobs as the diff, including temporary snapshot blobs for uncommitted content, not live disk contents. Review quotes are persisted independently of temporary snapshot files. Syntax highlighting pauses above approximately one million characters, with a notice, while the complete text remains visible. A version larger than 24 MiB explicitly reports that its full text cannot be loaded; it is never silently truncated. The syntax engine is a locally bundled highlight.js 11.11.1 (`vendor\highlight.mjs`), with its license in `vendor\highlight.LICENSE`. It does not depend on a CDN or send source code to external services.

Partial clones also remain offline. The canvas first reads change metadata from existing trees, then checks in batches whether each required historical blob is local. Working-tree file existence is not used as a filter. Files with missing historical objects are explicitly counted and named as skipped, without blocking other comparable files or treating skips as "no changes". Statistics and text diffs are computed only for files whose required objects are available. Every Git command sets `GIT_NO_LAZY_FETCH=1`; there is no download cache or automatic fetch path. If even the trees are missing and changes cannot be enumerated, the canvas reports an error instead of downloading or inventing results.

Recent repositories, selected files, view modes, wrapping preferences, and the uncommitted-changes option are saved in the extension's `artifacts\preferences.json`, keyed by worktree path rather than panel instanceId. New panels and extension reloads read the current branch again instead of reusing old comparison refs; ordinary page refreshes preserve the current panel's comparison.

All interface assets are local, without CDN dependencies or external uploads. The server listens only on `127.0.0.1` and uses a random capability URL, Host validation, and a required JSON POST header. Sandboxed iframes without `allow-same-origin` or `allow-forms` are supported: credential-free CORS for `Origin: null` is allowed only under the valid random path, including module scripts, fetch preflights, and SSE. Other external origins remain blocked. Buttons call the API directly rather than relying on HTML form submission, which the sandbox disallows.

## Development and validation

From the repository root, run `npm ci --ignore-scripts` to install development dependencies, then `npm test` for `git.test.mjs` and `reviews.test.mjs`. These cover diff semantics, sandbox HTTP endpoints, automatic worktree detection, configuration precedence, review references, idempotent sending, replies, resolution, and persistence.

Run `npm run test:browser` from the repository root for `renderer.test.mjs` and `review-renderer.test.mjs`. These use an installed Microsoft Edge in headless mode and a real `sandbox="allow-scripts"` iframe to check automatic loading, diffs, navigation, comparison controls, refresh, code selection, commenting, replies, collapsed threads, and outdated references. Playwright is a development dependency, not a runtime requirement.

Tests create and clean up disposable fixtures rather than using personal repositories. Git and browser tests create fixture directories under the current working directory; review unit tests use the OS temporary directory. Browser tests inject a mock send function and never submit test requests to a real conversation.
