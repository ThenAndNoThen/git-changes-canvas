# Git Changes

A user-scoped Git diff canvas that never modifies the inspected workspace or downloads Git objects. All interface labels, hints, and errors are in English; the header omits the Git command and automatic-selection status row. "Local" means that the Git object database already contains the required data, not that files must exist in the working tree; added, deleted, and un-checked-out files are supported. When opened in a repository session, the canvas resolves the current worktree from SDK `ctx.session.workingDirectory` (not the main checkout or the SDK's session artifact directory), selects the checked-out branch as target B, and loads changes automatically. Base A defaults to the remote default branch referenced by `origin/HEAD`, then the sole remote HEAD, the current branch's upstream, or finally HEAD. It never guesses main/master. Detached HEAD uses `HEAD`. Only conversations without a Git workspace fall back to the most recent repository. Branch inputs also accept tags, commit SHAs, `HEAD~3`, and other Git revisions; click "Compare / Refresh" or press Enter in an input to compare. Remote branches use existing local remote-tracking refs and are never fetched automatically.

Repositories without an initial commit still get their path and current branch filled in automatically; initialization does not fail because `HEAD` does not yet resolve to a commit. The default comparison shows "No commits on this branch". After creating the first commit, click "Compare / Refresh" to continue without reopening the panel.

- **Since divergence · A...B**: follows the direction of `git diff A...B`, comparing the common ancestor with B to show B's changes since divergence using local Git objects. Swapping A and B changes the result. Missing or multiple merge bases produce an explicit error; use endpoint comparison instead.
- **Endpoints · A B**: compares two commits using `git diff A B` (or `git diff A..B`) without checking out their files.
- Search changed files on the left. Addition and deletion counts appear only when greater than zero (`+0` / `-0` are omitted; binary indicators remain). The right pane supports split/unified diffs, line numbers, word-level emphasis, wrapping, and horizontal scrolling. Added and deleted content has distinct green/red backgrounds and gutter accents in both light and dark themes. Drag the divider to resize the file list.
- Diff and full-file views support syntax highlighting for C#, Java, Kotlin, JavaScript/TypeScript, Python, C/C++, Go, Rust, JSON, XML, YAML, Markdown, and other common formats. Highlighting uses the complete local versions on both sides, so omitted diff context does not reset multiline comments or strings. Unknown formats use plain text.
- "Full file" supports "Split" and "Single column" layouts. Split view shows the complete comparison base (the common ancestor for `A...B`) and target B, aligning both sides by change blocks. Blank cells compensate for insertions and deletions without omitting unchanged content. Single-column view shows target B, or the base for a deleted file. Both layouts retain line numbers, syntax highlighting, wrapping, arrow controls, `F7` / `Shift+F7`, and cross-file navigation. Full-file and layout settings persist while navigating between files. In single-column view, pure deletions have navigable markers, including at the beginning or end of a file and when a file is emptied; these markers are not file content. Switching between full-file and diff views or layouts preserves the active change. Settings are saved per repository. Binary files and submodules explicitly report that ordinary full-text views are unavailable.
- Toolbar arrows, `F7` / `Shift+F7`, and `Alt+Down` / `Alt+Up` navigate change blocks, moving to the next or previous file in the filtered list at file boundaries. Binary and permission-only changes are also shown. Cross-file rename detection is disabled to avoid reading nonlocal rename candidates; renames appear as additions and deletions within the comparison. `Ctrl+P` focuses the file filter.

## Review comments

In diff or full-file view, hover over a line number and click the `+` on its left to comment on that line. Selecting code on one side also reveals a `+` beside the last selected line. You can click a line number, Shift-click another to select multiple lines, then click `+` to comment on the range. The control supports keyboard focus and Enter/Space; there is no separate toolbar comment button. References support partial-line columns and multiline ranges, with limits of 200 lines and 16000 characters. The server extracts the reference from the pinned Git blob rather than accepting arbitrary code text from the browser.

Clicking "Send to conversation" queues the comment into the session that owns this canvas through SDK `session.send`, not another open chat or a remote pull request. The main agent receives the file, revision, range, original text, and handling instructions. It uses `git_changes_review_read` / `git_changes_review_reply` to respond in the same thread when finished or blocked. Existing session mode, permissions, and approval flows are preserved; permissions are not elevated and workspaces are not switched automatically. Sending a comment uses the current session's model allowance. Missing persistent session storage produces an explicit error rather than falling back to temporary comments that would be lost.

New comments use SDK `displayPrompt` to appear concisely in the conversation as `Review inline code: path:L10`; follow-up replies appear as `Reply to thread: path:L10`. Multiline ranges use `L10-L15`. The agent still receives the full comment, pinned code reference, and handling instructions, and the original comment remains unchanged in the canvas. This is a compact message presentation, not the native review card's collapse protocol, and it does not rewrite previously sent messages.

Users can follow up with "Send reply" or choose "Resolve"; agent replies never resolve a thread automatically. Resolved threads collapse by default and can be expanded to view their history or reopened. The previous/next comment controls navigate unresolved threads by file and reference position, independently of diff navigation. They work across files and open the split full-file view when locating code. If the code changes, the original reference is preserved and marked outdated; old line numbers are never applied to the new version.

Comments are stored in `files\git-changes-reviews.json` under the owning session's workspace, organized by repository, comparison refs, and thread UUID. They do not depend on the panel's instanceId and are not written into the inspected code repository. They survive refreshes, panel reopening, and extension reloads. Panels in the same session receive synchronized replies. Failed or uncertain delivery preserves the comment and displays a warning; automatic retries are avoided to prevent duplicate handling. Check the owning conversation before resending. Unsent input drafts are not persisted comments and may be lost on page reload.

Use `open_canvas` with `canvasId: "git-changes"` and an instanceId of your choice. No path or branch is required. Optional input such as `{ "repo": "C:\\work\\repo", "base": "origin/main", "target": "HEAD", "mode": "merge-base" }` explicitly overrides automatic defaults; saved history does not override these parameters. The `compare`, `get_state`, and `get_file` agent actions are supported. `compare` returns at most 30 file entries, while the canvas displays the complete list. `get_state` also returns workspace provenance and HTTP diagnostic counts. `get_file` accepts `includeSources: true` to return the complete local Git text for the comparison base and target; by default, it returns only the diff.

Comparisons use pinned commit SHAs so branch movement cannot make the file list and details inconsistent. Refreshing resolves refs again and checks whether historical objects are local. The repository is never modified: no branch switching, external diff/textconv execution, or repository scripts. Each Git command has a 24 MiB output limit and a 60-second timeout; exceeding either produces an explicit error instead of truncation. File lists and details load on demand; narrow the range for very large comparisons.

Full-file views also read pinned Git blobs, not uncommitted disk contents. Syntax highlighting pauses above approximately one million characters, with a notice, while the complete text remains visible. A version larger than 24 MiB explicitly reports that its full text cannot be loaded; it is never silently truncated. The syntax engine is a locally bundled highlight.js 11.11.1 (`vendor\highlight.mjs`), with its license in `vendor\highlight.LICENSE`. It does not depend on a CDN or send source code to external services.

Partial clones also remain offline. The canvas first reads change metadata from existing trees, then checks in batches whether each required historical blob is local. Working-tree file existence is not used as a filter. Files with missing historical objects are explicitly counted and named as skipped, without blocking other comparable files or treating skips as "no changes". Statistics and text diffs are computed only for files whose required objects are available. Every Git command sets `GIT_NO_LAZY_FETCH=1`; there is no download cache or automatic fetch path. If even the trees are missing and changes cannot be enumerated, the canvas reports an error instead of downloading or inventing results.

Recent repositories, selected files, view modes, and wrapping preferences are saved in the extension's `artifacts\preferences.json`, keyed by worktree path rather than panel instanceId. New panels and extension reloads read the current branch again instead of reusing old comparison parameters; ordinary page refreshes preserve the current panel's comparison. Only committed branch contents are compared; uncommitted and untracked files are excluded.

All interface assets are local, without CDN dependencies or external uploads. The server listens only on `127.0.0.1` and uses a random capability URL, Host validation, and a required JSON POST header. Sandboxed iframes without `allow-same-origin` or `allow-forms` are supported: credential-free CORS for `Origin: null` is allowed only under the valid random path, including module scripts, fetch preflights, and SSE. Other external origins remain blocked. Buttons call the API directly rather than relying on HTML form submission, which the sandbox disallows.

Run `node --test git.test.mjs` from this directory to verify diff semantics, sandbox HTTP endpoints, automatic worktree detection, and configuration precedence. Test repositories are created only in temporary directories, without accessing real repositories. Browser regressions are in `renderer.test.mjs`: from a development directory with Playwright installed, run `node <extension-path>\renderer.test.mjs`. It uses local Edge in headless mode and a real `sandbox="allow-scripts"` iframe to check automatic loading, diffs, navigation, the compare button, Enter, and refresh. The extension itself does not require Playwright at runtime.

Review tests: `node --test reviews.test.mjs` checks references, idempotent sending, replies, resolution, and persistence. From a development directory with Playwright installed, run `node <extension-path>\review-renderer.test.mjs` to verify selection, commenting, replies, collapsed threads, navigation, and outdated references in a real sandbox. Browser tests inject a mock send function and never submit test requests to a real conversation.
